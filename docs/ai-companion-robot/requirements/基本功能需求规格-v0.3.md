# AI 陪伴机器人基本功能需求规格

> 版本：v0.3  
> 日期：2026-08-22  
> 状态：开发基线草案。本文优先级高于 v0.1 中与一期范围冲突的描述。  
> 一期目标：面向在日本生活的中国东北老人，完成 50 台功能丰富的试产样品；运营规模化能力可在二期完善。

## 1. 产品与系统边界

### 1.1 一期参与端

1. 机器人头部：MTK Android 14、420×420 触摸屏，承担收音、播放、本地唤醒、表情、对话状态与 ESP32 通信。
2. ESP32/外包硬件：毫米波雷达、声音事件、声源方向和机械执行由外包方实现；本项目负责定义并实现 Android 侧通信接口。
3. 服务端：基于 `xiaozhi-esp32-server`，部署在日本，承担语音、LLM、人设、记忆、设备和通知能力。
4. 家属端：基于现有 `manager-mobile` 的 uni-app 跨平台能力，设计并实现 iOS/Android 简单设置功能。
5. LINE：家属账号关联、告警推送和白名单设置命令。
6. 管理后台：沿用 `manager-web`，供当前管理员查看对话、管理设备、Prompt 和测试音频。

### 1.2 一期包含

- 双级唤醒与自动休眠。
- 连续语音对话、服务端 VAD、用户打断。
- 豆包语音 2.0 首选接入；保留其它语音模型和自部署模型 Provider。
- OpenAI/Gemini 对话模型的可配置接入和对比评测。
- 东北方言人设、性格维度、情感回应和表情联动。
- 连续声源跟踪的 Android—ESP32 协调。
- 一设备一主账号、可选多人声纹子账号。
- 多家属—多设备绑定；一期所有已绑定家属均为管理员。
- 提醒、基础主动对话、设备状态监控和 Prompt 管理。
- 对话文本长期保存；测试阶段原始音频可配置保存和手动清理。
- 基础长期记忆、Line 告警与家属设置。
- 日本公共与本地生活信息的通用接入骨架、来源透明和订阅触发能力；首批具体数据源按调研结论逐个启用。

### 1.3 一期暂缓

- 尚未通过来源、许可、覆盖度和样例验收的日本本地数据源；不得仅因已有 URL 就承诺上线。
- 喜马拉雅/音乐内容接入。
- 家属端完整运营、客服和审计角色体系。
- Android/ESP32 OTA，除非试产维护评审决定提前。
- 摄像头、红外和其它智能家居功能。

## 2. 角色与权限

| 角色 | 一期权限 |
|---|---|
| 老人主用户 | 语音对话、语音设置、提醒、删除/纠正记忆的语音入口 |
| 声纹子用户 | 被识别后使用自己的短期上下文和称呼；不自动取得管理权限 |
| 绑定家属 | 一期均可查看设备状态、设置人设/提醒/免打扰、接收告警；可通过 App/LINE 操作 |
| 平台管理员 | 查看长期对话文本、管理测试音频、设备、模型、Prompt 和异常日志 |
| 外包硬件 | 只通过设备协议提供传感器/动作能力，无业务数据访问权 |

一期“所有家属均为管理员”仍需保留操作审计、操作者 ID 和最后修改时间。涉及解绑全部家属、恢复出厂、删除账号等高风险操作必须二次确认。

老人语音只允许修改低风险偏好，例如音量、亮度、称呼、方言/幽默程度、回复长度、免打扰和主动对话开关。删除账号、解绑最后一名家属、恢复出厂、导出/删除长期数据、修改安全联系人等敏感操作，不得仅凭当前语音直接执行；必须转家属 App/后台完成强认证与二次确认。声纹可用于个性化，不作为一期敏感操作的唯一身份凭据。

## 3. 双级唤醒与休眠需求

### 3.1 电源状态定义

| 状态 | Android/屏幕 | 收音能力 | 唤醒来源 |
|---|---|---|---|
| `ACTIVE` | 系统运行、屏幕显示 | 正常收音/对话 | 无需唤醒 |
| `STANDBY_LISTEN` | 屏幕关闭或低功耗表情，CPU/音频链路可用 | 本地唤醒词模型持续工作 | 本地唤醒词、触屏/按键、ESP32 事件 |
| `SUSPENDED` | Android SoC 真正 suspend | 普通 App 不可持续收音 | ESP32 硬件唤醒信号/系统级 wake-up sensor |
| `WAKING` | 从休眠恢复 | 尚不可接受对话 | 等待系统、音频、网络和协议恢复 |
| `OFFLINE` | 系统运行但云端不可用 | 可本地检测唤醒词 | 网络恢复或用户重试 |

`STANDBY_LISTEN` 与 `SUSPENDED` 必须在功耗测试中分别记录，不能统称“休眠”。Android 官方将 suspend 定义为 SoC 不供电的低功耗状态，普通应用逻辑无法在该状态持续执行；因此 ESP32 唤醒真 suspend 必须有 MTK/板级硬件通道。[AOSP suspend 说明](https://source.android.com/docs/core/interaction/sensors/suspend-mode)

### 3.2 一级唤醒：ESP32

触发条件：

- 毫米波雷达从“无人”变为“有人”；
- ESP32 声音检测达到配置阈值；
- 物理按键/触摸等外部事件（预留）。

行为：

1. 若 Android 为 `SUSPENDED`，ESP32 先拉起硬件唤醒信号，再等待 Android 通信链路恢复。
2. ESP32 发送带原因、时间、置信度和序号的 `WAKE_EVENT`。
3. Android 进入 `WAKING`，短时持有有超时的 WakeLock，恢复音频和网络；WakeLock 只能覆盖恢复/对话窗口，不得永久持有。Android 官方建议仅在必要时短时使用并尽快释放。[Android WakeLock 指南](https://developer.android.com/develop/background-work/background-tasks/awake/wakelock)
4. “检测到有人”默认只把系统带入 `STANDBY_LISTEN`，不立即将环境声音上传云端，也不自动发起对话；主动对话策略另行判断。
5. 声音事件同样只激活本地唤醒词窗口，除非声音被硬件定义为独立安全告警。

### 3.3 二级唤醒：Android 本地唤醒词

- 在 `STANDBY_LISTEN` 使用本地模型持续处理麦克风 PCM，不把待机音频上传或保存。
- 首期唤醒词和模型由产品/算法确认；至少支持东北口音测试。
- 检测成功后保存 300–800 ms 环形前滚音频，避免吞掉唤醒词后的首字；实际长度经测试确定。
- 唤醒后进入 `LISTENING`，播放短提示音/表情；提示音必须与开始收音时序协调。
- 误唤醒后若服务端 VAD 在超时内未检测到有效语音，自动回到待机。
- 播报时必须避免机器人自己的声音触发唤醒；优先使用 MTK AEC/参考信号，其次暂停唤醒词或使用专门的打断模型。

### 3.4 Android 14 常驻约束

- 设备应采用专用设备/Device Owner 或系统签名能力，确保开机启动、kiosk 和后台音频策略可控。
- Android 14 对后台启动麦克风前台服务有限制；普通后台 App 不能假设被 ESP32 消息唤起后即可取得麦克风。系统组件、Device Owner、`VoiceInteractionService` 或特权权限路线需与 MTK 固件方确认。[Android 14 后台前台服务限制](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)
- 应在首次可见设置流程中完成麦克风授权和服务初始化，避免休眠后才首次请求权限。

### 3.5 自动休眠

进入 `STANDBY_LISTEN` 的条件全部满足：

- 当前无对话、无播报、无提醒/告警；
- 最近一次有效交互超过 `idleTimeout`；
- ESP32 在场状态为无人，或主动对话策略判断无需保持活跃；
- 不处于禁止休眠的维护任务。

从 `STANDBY_LISTEN` 进入 `SUSPENDED` 需满足更长的 `deepSleepTimeout`，且 ESP32 硬件唤醒链路已通过验收。夜间默认更快进入深休眠，但提醒和安全告警仍可唤醒。

## 4. 语音对话需求

### 4.1 主流程

`WAKE → LISTENING → ASR → THINKING → TTS/SPEAKING → LISTENING 或 STANDBY`

- ASR/TTS 首选豆包语音 2.0；必须新增 Provider 或升级现有旧版豆包接口，不能修改通用编排逻辑来绑定供应商。
- LLM 至少实现 OpenAI-compatible 和 Gemini 两类 Provider 配置，生产只启用通过日本网络/隐私评审的组合。
- 对话文本和模型/Prompt 版本按轮次持久化。
- 服务端低置信 ASR、空文本和模型超时均给出可理解的简短反馈。
- 网络不可用时客户端本地播报固定提示，如“网络不好，请检查网络”，然后回到可唤醒待机。

### 4.2 连续对话与打断

- 第一可用版本采用回合制：播报结束后自动重新收音。
- 用户触屏/实体动作中断为 P0；发送 `abort` 前先停止本地播放并清空旧音频。
- 语音打断在 AEC 和误触发测试通过后开启。
- 每轮使用 `sessionId + turnId`；晚到的旧轮次音频/表情不得执行。

### 4.3 方言与语言

- 默认生成东北方言表达，避免过度堆砌方言导致幼稚化或理解困难。
- 识别以中文/东北口音为主，允许中文中夹杂少量日语词；建立独立混合语言测试集。
- 初期通过 Prompt、词表纠错和 Provider 参数增强；只有评测证明不足时才启动微调。

## 5. 人设、情感与表情

- 性格维度：方言程度、幽默程度、新词程度、主动程度、回复长度、共情程度，统一 0–100，但映射为离散 Prompt 规则。
- 老人语音设置优先；家属可通过 App/LINE 修改明确的设置项，最后一次有效设置生效并保留审计。
- 情感识别输出 `emotion/intensity/confidence`，用于回复语气和表情，不做医疗判断。
- 服务端下发表情语义：`neutral/listening/thinking/happy/sad/surprised/concerned/sleep/error`；Android 映射到用户提供的 420×420 表情资源。
- 表情包需有资源 manifest：资源版本、文件哈希、循环方式、进入/退出动画和最低客户端版本。

## 6. 声源跟踪需求

- ESP32 在对话期间持续上报声源角度、置信度和时间；建议有效说话期间 5–10 Hz。
- Android 根据当前 VAD、声纹和最近对话人选择 `activeSpeaker`，向 ESP32 下发跟踪目标/启停指令。
- 单人时连续跟随；多人规则一期采用“当前有效语音 + 最近成功 ASR 轮次对应的方向”，置信度不足时保持当前位置，不来回摆动。
- 机械限位、限速、堵转和执行安全由外包硬件负责；Android 只能发送语义目标，不能直接发送 PWM。

## 7. 账号、绑定和家属端

- 家属 App 登录支持邮箱一次性验证码和 LINE Login；一期不支持手机号和邮箱密码登录。验证码必须短时有效、单次使用、限制发送/尝试频率，并避免通过响应泄露邮箱是否已注册。
- 一台机器人绑定一个主账号；一个家属可绑定多设备，一台设备可绑定多个家属。
- 设备激活使用一次性码；绑定、解绑和恢复出厂均需审计。
- 家属 App 基于现有 `manager-mobile`（uni-app/Vue 3）裁剪实现，避免两人团队再建第四套客户端技术栈。
- 一期 App 页面：登录/注册、设备绑定、设备列表/状态、音量/亮度、人设参数、提醒、免打扰、主动对话开关、告警联系人、解绑。
- 一期不向家属展示完整对话历史；对话文本只对平台管理员开放。

## 7.1 日本公共与本地生活信息

- 信息服务必须遵循“事实获取与人格表达分离”：连接器只产生带来源、抓取时间、有效期和地理范围的结构化事实；LLM 只负责结合用户偏好生成自然语言。
- 明确查询采用信息回答模式：先给结论，再说明来源、资料时间和不确定性。主动播报采用拟人模式，但不得改变事实、严重度或时效信息。
- 官方来源优先于运营方、商业机构和通用网页搜索。无法获得权威数据时允许使用通用搜索 Provider，但必须保留结果 URL，并向用户说明这是网络搜索结果而非官方结论。
- 第一期主动信息由订阅、计划任务和传感器事件在客户端触发；暂不把服务端实时推送作为前置依赖。每次只选择 1–3 条与用户所在地和偏好最相关的内容，并服从免打扰与频控。
- 初始候选来源包括气象厅防灾 XML、环境省暑热指数和 ODPT 公共交通数据；每个来源在开发前必须完成覆盖区域、许可/署名、认证、频率、缓存、故障降级和样例数据验收。
- 通用数据模型、来源调研清单、连接器接口和验收规则见《日本公共与本地生活信息服务详细设计-v0.1.md》。

## 8. 提醒、主动对话与 LINE

### 8.1 提醒和主动对话

- 提醒包含名称、时间/重复规则、时区、启用状态、创建来源和最后修改人。
- 统一使用 `Asia/Tokyo` 计算用户日程；数据库存 UTC + IANA 时区。
- 主动对话需要同时通过：有人在场、非免打扰/夜间、距离上次主动对话超过频控、设备空闲。
- 无人或未响应的提醒按策略重试/转家属通知，规则下一轮细化。

### 8.2 LINE 告警

- 使用 LINE Official Account + Messaging API；家属需完成账号关联并将官方账号加为好友。
- 传感器告警先形成平台 `Alert`，状态为 `OPEN/ACKED/RESOLVED/CANCELLED`，再异步向所有绑定家属发送 push。
- 每次推送使用业务幂等键映射 `X-Line-Retry-Key`，避免网络重试产生重复告警。LINE 官方支持 push 并建议可重试接口始终携带 retry key。[LINE 发送与重试](https://developers.line.biz/en/docs/messaging-api/sending-messages)、[LINE Retry Key](https://developers.line.biz/en/docs/messaging-api/retrying-api-request/)
- LINE webhook 必须验证签名、快速返回 2xx、异步处理并按 event ID 幂等。LINE 官方明确要求验证签名并建议异步处理。[LINE Webhook](https://developers.line.biz/en/docs/messaging-api/receiving-messages)
- LINE 设置命令只开放白名单：音量、亮度、人设、免打扰、提醒和主动对话；删除、解绑和恢复出厂不通过聊天文本直接执行。
- 当前传感器告警规则由外包硬件和产品后续提供；一期先实现统一事件接口和模拟告警。

## 9. 记忆与声纹

- 对话文本长期保存；每轮包含设备、主账号、可选声纹子用户、时间、ASR 文本、回复、Prompt/模型版本和安全标签。
- 原始音频生产默认不保存；测试环境通过配置保存到受控目录，记录保留标签并支持管理员批量/手动删除。
- 长期记忆自动提取，类型包括个人资料、关系、偏好、重要事件、习惯和经历；保留来源轮次与置信度。
- 用户说“不是这样”“忘掉这件事”时支持纠正/删除；自动记忆不等同永久不可修改。
- 声纹为试验功能：一个主账号下可建立多个声纹子用户；识别置信度不足时回退主用户上下文，不猜测身份。

## 10. 设备状态与 Prompt 管理

- 状态：在线、Android/应用版本、ESP32 版本、网络、音量/亮度、当前电源/对话状态、最近心跳、传感器摘要和错误码。
- Android 与 ESP32 心跳分开；“Android 在线”不代表“ESP32/雷达正常”。
- Prompt 必须版本化，包含草稿、测试、发布、回滚状态；支持按内部设备/设备组灰度。
- 每轮对话记录实际使用的 Prompt 版本；禁止直接覆盖已发布版本正文。

## 11. 非功能需求和候选验收门槛

| 类别 | 一期候选门槛（M0 基准后冻结） |
|---|---|
| ESP32 唤醒 | 事件发生到 Android 进入 `STANDBY_LISTEN` P95 ≤ 2 s |
| 本地唤醒词 | 1–3 m 目标样本召回 ≥95%，家庭环境误唤醒 ≤0.5 次/小时 |
| 对话延迟 | 说完到首段可听语音 P50 ≤1.5 s、P95 ≤3 s |
| VAD | 慢语速截断率 ≤2%，最大尾等待 P95 ≤1.5 s |
| 稳定性 | 单机 72 h 无 S0/S1；50 台 7 天无批量离线 |
| 状态监控 | 在线状态延迟 ≤90 s，关键告警进入平台 ≤5 s（不含 LINE 外部延迟） |
| 数据 | 生产原始音频保存率 0；所有管理查看/修改均有审计 |
| 恢复 | 网络恢复后 P95 30 s 内重新可对话 |

上述唤醒率和 VAD 数值为工程起始目标，不是已验证承诺；需用东北老人、日语夹杂和目标硬件实录集确认。

## 12. 一期验收场景

1. Android suspend 时，雷达检测有人，ESP32 唤醒 Android；Android 不上传环境音，只进入本地监听。
2. 用户说唤醒词并以慢语速提问，机器人完成方言回复和表情联动。
3. 对话中用户移动，机器人持续面向主要说话人；多人噪声时不高频来回转动。
4. 用户手动或语音打断播报，新轮次不播放旧音频。
5. 断网时本地给出固定提示；恢复网络后自动可用。
6. 老人语音设置幽默程度，家属后续从 App/LINE 修改，系统记录来源和最后生效值。
7. 管理员发布新版 Prompt 到试验设备并成功回滚。
8. 模拟传感器告警，所有绑定 LINE 家属收到一次通知并可确认。
9. 对话事实自动进入记忆，用户可通过语音纠正/删除。
