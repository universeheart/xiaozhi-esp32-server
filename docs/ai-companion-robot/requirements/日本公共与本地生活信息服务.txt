1、文档目的与产品定位
本功能的目标不是简单地把机器人做成“会查网页的智能音箱”，而是让机器人能够感知用户所在地区正在发生的事情，理解这些事情与用户的关系，并以符合用户性格和双方关系的方式主动交流。

2、核心产品原则
事实与表达分离：事实层由可靠数据源确定；表达层可根据人格、情境和用户偏好进行拟人化改写。
来源透明：正式查询回答应说明来源；商业平台和用户评论不得冒充官方事实。
位置相关：优先提供与用户住所、当前位置、常用线路、常去店铺和生活习惯直接相关的信息。
少而有用：主动播报不追求信息数量，应优先选择“今天与用户最有关的1至3件事”。

3、用户与“个人生活圈”基础数据
系统首次配置时应建立用户的“个人公共信息圈”和“附近生活圈”。缺少这些数据时，机器人只能提供全国性信息，无法形成真正的本地陪伴。
位置：邮政编码、都道府县、市区町村、町名、常住地址、当前位置授权
公共事业：供电公司、燃气公司、水道局
交通：常用铁路线路、车站、公交线路、常用出行时段
本地生活：常去超市、药妆店、商店街、餐馆、医院、药局
社区关系：自治会/町内会、住宅管理组合、公民馆、国际交流协会
表达偏好：语言、方言、称呼、幽默程度、粗口等级、禁用词、敏感话题
主动性：允许主动播报的时段、频率、类型、勿扰时段（主动播报说明：主动播报，主要是客户端根据该用户之前的对话完成了订阅，通过定时或者某些条件触发的对话流程。暂时不实现主动推送系统消息，后面实现主动推送的播报，也是通过安卓推送，先推送消息，再由客户端触发通话流程）

4、API与数据接入
日本气象厅 JMA	天气、警报、地震、海啸、火山	XML Feed：regular.xml / extra.xml / eqvol.xml / other.xml	无需注册；需缓存、重试和去重
环境省 WBGT	暑热指数实况/预测	GET https://www.wbgt.env.go.jp/api/v1/getSurveyData	按官方API说明；控制频率
ODPT	铁路/公交实时与静态数据	https://api.odpt.org/api/v4/{dataType}	需注册并取得API Key；覆盖依运营商
以上供参考，我们后续会提供准确信息来源。
对于没有提供信息来源的问题，需要有一个通用的搜索方案，比如到google搜索。对于此类，回答可以加上“我到google查了一下”。

5、对话模式与拟人化表达引擎
5.1 两种基本对话逻辑
模式	触发	表达要求	示例
信息回答模式	用户主动、明确提问	相对正式；先给答案；必要时说明来源、时间和不确定性	“日本气象厅今天的预报显示，最高气温36度，下午尽量减少外出。”
拟人化主动表达模式	机器人主动播报、提醒、贫嘴或顺势接话	从机器人感受、双方关系和当前情境出发；可调侃、吐槽、使用方言或经授权的粗口	“我操，外头36度，我肚子里也快成小蒸笼了，咱开会儿空调呗。”

5.2 人格与粗口等级
0 正式型	不使用粗口，表达克制	“今天气温较高，请注意防暑。”
1 熟人型	自然口语、关心、轻吐槽	“今天可真够热的，下午就别出去硬晒了。”
2 嘴贫型	东北式调侃、接话茬、轻度夸张	“外头跟蒸笼似的，你还非得这会儿出去啊？”
3 放飞型	用户明确允许后，可使用“我操”“他妈的”等口语	“我操，这天儿是真不让人活，赶紧开空调。”
配置要求
粗口等级必须由用户明确选择或长期互动确认，不应默认开启。支持禁用词、家人在场自动收敛、夜间低打扰、情绪低落时自动切换温和模式。
人格与粗口等级的实现需要再讨论，用户提出的“家人在场自动收敛”、“情绪低落时自动切换温和模式”都是比较难实现的。

5.3 主动表达触发逻辑
官方事件	高温、警报、线路停运、社区活动	生成与用户相关的提醒
设备传感器	机身内部温度高、室内温度高、噪声变化	以“机器人自身感受”切入
用户行为	准备出门、长时间未活动、刚问过相关话题	及时劝阻、建议或顺势聊天
时间与习惯	固定买菜时间、常用通勤时段、垃圾日前夜	提前而不过早提醒
位置与距离	活动在步行15分钟内、常去超市有折扣	只推荐真正可达的内容
以上是客户提出的逻辑，第一个阶段，我们还是以客户订阅和传感器触发，进行客户端触发。
