# AI 陪伴机器人对话 MVP 开发计划

> 版本：v0.2  
> 状态：已被《开发计划-v0.3.md》取代，仅保留“只做对话 MVP”时的历史估算。  
> 范围：日本部署、MTK Android 14、服务端 + 机器人对话客户端。  
> 暂不包含：机械/底座、声源定位、家属 App、长期记忆、正式日本搜索内容。

## 1. 推荐周期和团队

建议 8–10 周完成可试点 MVP，前提是 MTK 样机和音频 SDK 第 1 周可用。

- Android/Flutter 1 人：客户端状态机、UI、协议。
- Android 音频/Kotlin 1 人：Audio HAL、AEC、前台服务、设备化。
- Python 服务端 1 人：实时链路、Provider、性能与安全。
- Java/Web/DevOps 0.5–1 人：manager-api、部署、监控。
- 测试 1 人：从第 1 周建设自动化，第 4 周起实机专项。
- 产品/Prompt 0.5 人：对话人格、语言样本、验收。

若只有 3 名研发，建议按 10–12 周排期，并将后台页面优化和自动打断延后。

## 2. 迭代安排

### Sprint 0：基线与风险清理（第 1 周）

- 冻结四仓库 commit，生成 `UPSTREAM.md`、SBOM 和许可证清单。
- 评审服务端上游差异，决定从当前 commit 升级还是锁定。
- 轮换本地配置中暴露的数据库凭据；清理默认 Token、Token 日志和 debug signing。
- 清理 Android 绝对 JDK/Gradle 路径，建立 Windows/CI 可复现构建。
- 获取 MTK SoC、Audio HAL、麦克风、扬声器和系统签名/Device Owner 条件。
- 冻结 WebSocket v1 协议样例和 mock server。

出口：两端可由 CI 构建；Secret 扫描无高危；真实样机能安装启动；协议基线有 tag。

### Sprint 1：可靠音频与连接（第 2–3 周）

- 重构 PCM ring buffer 和 60 ms Opus 连续分帧。
- 拆分 Capture/Encoder/Playback，增加音频帧守恒与 golden 测试。
- 实现显式连接/握手/对话状态机、超时、指数退避和网络感知。
- Token 使用 Android Keystore，设备激活流程先用内部最小版本。
- 服务端增加 Trace、客户端版本和分段延迟指标。
- `py-xiaozhi` 增加协议冒烟和固定音频回放脚本。

出口：随机 PCM 分块不丢样本；连续 100 次连接/断线无卡死；可完成 20 轮对话。

### Sprint 2：MTK 设备化与半双工体验（第 4–5 周）

- Kotlin Robot Service：开机启动、前台常驻、Flutter 桥、崩溃恢复。
- 音频焦点、路由、播放器队列和跨轮音频隔离。
- 服务端 Silero VAD 老年慢语速参数化；建立录音评测集。
- 状态/表情页面改为机器人界面，移除普通手机聊天 App 非必要入口。
- 日本区域测试环境、WSS、私网 MySQL/Redis、内部 manager-web。
- ASR/LLM/TTS 候选在日本网络上的准确率、延迟、成本和数据处理地基准。

出口：样机冷启动后自动可用；30 分钟半双工对话无崩溃/假连接/跨轮播放。

### Sprint 3：AEC、打断与弱网（第 6–7 周）

- 验证 MTK HAL AEC/NS/AGC；按音量和距离形成报告。
- AEC 合格后开放播报中上行和语音打断；否则保留按钮中断与半双工。
- 有界音频队列、网络切换、服务端供应商超时/熔断和用户可理解降级。
- Prompt 人设、情感/表情语义和版本配置的最小闭环。
- 数据保留、日志脱敏、同意/删除最小链路。

出口：目标场景打断指标达到评审阈值；弱网不会无限积压；所有供应商故障均可恢复或清晰降级。

### Sprint 4：试点门禁（第 8–9 周）

- 72 小时长稳、1/3/5 米、家庭噪声、东北口音/日语需求对应测试。
- 安全扫描、越权、Token 吊销、日志抽查、备份恢复和回滚演练。
- 日本 APPI 数据流与供应商条款专业评审；完成日文/中文隐私告知。
- 5–10 台内部试点，按 S0–S3 缺陷分级收敛。
- 运维手册、仪表盘、告警、版本兼容表和已知问题。

出口：详细设计中的 MVP 完成定义全部有证据；S0/S1 为 0，批准进入扩大试点。

### 缓冲/试点修复（第 10 周）

处理硬件音频、供应商或日本网络基准暴露的问题。若前序无关键延期，可用于日本搜索 Provider 接口和 mock 实现。

## 3. 关键路径

```text
MTK 样机与 Audio HAL 资料
 → Android 可复现构建
 → PCM/Opus 正确性
 → WSS 状态机
 → 日本环境端到端
 → 声学/AEC
 → 72h 长稳
 → 小规模试点
```

最主要的日期风险不是 LLM 接口，而是 MTK 音频驱动、同时录放/AEC 能力以及硬件到货。若第 2 周仍没有样机，立即使用 Android 14 普通设备推进协议，同时将正式试点日期按样机延误顺延。

## 5. 第一周需要用户/硬件方提供

1. MTK SoC/开发板型号、系统镜像、ADB/系统签名权限。
2. Audio HAL/AudioPolicy 配置、麦克风阵列通道与 AEC/NS/AGC SDK。
3. 日本云厂商/区域偏好和现有账号。
4. 是否允许语音/文本送往中国境内模型服务。
5. 第一批用户语言及 MVP 入口方式。
6. 文本/音频保留规则和计划试点日期。
