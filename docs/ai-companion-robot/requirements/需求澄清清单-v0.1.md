# AI 陪伴机器人需求澄清清单

> 请优先回答 P0。可以直接在每个问题下方填写“答：”，我会据此更新详细设计与计划。

## P0：决定架构与首期范围

1. 首批用户和使用地点是什么：主要是在日本生活的中国东北老人，还是中国国内老人？计划试点多少台、量产目标多少台？  
   答：产品主要部署在日本。主要面向的用户是生活在日本的中国东北老人。首先试产50个样品，样品要求功能尽量丰富，但实际运营方面的支持功能可以放在二期。

2. 已选或候选的头部主控、Android 版本、麦克风阵列、屏幕、底座 MCU 和舵机型号分别是什么？现有硬件样机/SDK/原理图何时可用？  
   答：头部使用 MTK 平台 Android 14；硬件目前我们只关注如何跟ESP32通讯，后面可能有Android驱动的开发，暂时可以都不做计划。。

3. “客户端”具体包括哪些：机器人 Android 端、家属手机 App、管理后台？家属端首期需要原生 Android、iOS、微信小程序还是 Web？  
   答：本期只规划机器人 Android 对话客户端，开始家属端（使用iOS和Android的跨平台APP）的设计工作，包括简单的设置工作即可，暂时不考虑其它客户端。

4. 首期必须上线的功能请从以下选择：连续语音对话、方言、人设设置、情感回应、表情、声源跟随、家属绑定、提醒、状态监控、Prompt 管理。哪些可以延期？  
   答：本期要完成所有上述功能。
   补充：开始对话采用双级唤醒。Android 真正休眠时，由 ESP32 在毫米波雷达发现有人或检测到声音后唤醒 Android；Android 处于可以收音的待机状态时，由本地模型识别唤醒词后进入对话。

5. 服务端计划部署在哪个国家/地区、使用哪家云？用户语音/文本是否允许发送到中国、日本或美国的第三方模型服务？  
   答：服务主要部署在日本，对话大模型目前考虑使用OpenAI或Gemini。

6. 豆包语音 2.0 是否已确定为首选？ASR、TTS、LLM 是否允许混用不同供应商？是否已有账号、配额和预算上限？  
   答：目前首选豆包语音2.0（开源代码目前只支持豆包旧版API，所以要更新代码）。其它模型或者自己部署模型，先做计划。第一个阶段，不考虑消耗量的预算。 

7. 是否要求弱网/断网仍能完成唤醒和若干本地命令？断网时必须支持哪些功能？  
   答：先做一个计划，一期最多只实现简单的回复即可，大概就是能说“网络不好，请检查网络”等。

8. 是否包含“紧急求救/通知家属”？若包含，触发条件、联系人渠道、误报确认和免责声明是什么？  
   答：会根据一些传感器的结果，判断需要给家属发警报，目前想接入Line。

9. 默认是否保存对话文本、原始音频和声学特征？各自保留多久？老人和家属谁能查看、导出和删除？  
   答：需要长期保存对话文本。目前只有管理员可以查看和操作。实际使用不需要保存音频，但测试阶段，可以以文件形式保存，可以配置是否保存，手动清理即可。

11. 开发团队的角色和人数、希望开始试点的日期、硬件预算及单设备云服务月成本上限是多少？  
    答：硬件、ESP32已经外包给其它公司开发。我们自己开发服务端和Android客户端。目前有两位开发。项目可以立刻开始。暂时不考虑服务器成本。
    补充：Codex 作为主要开发力量，两位人工开发作为协作助手，负责提供信息、账号/权限、真机与物理设备操作、硬件团队沟通及人工验收。每个小阶段必须可理解、可测试并留下验收证据。50 台样品完成日期暂未确定。

## P1：影响详细交互与数据设计

12. 机器人是否支持一台设备服务多位老人？如何区分说话人，是否需要声纹？  
    答：一台机器人支持一个账号，目前开源项目介绍里，包含声纹识别，可以尝试区分多个人，建立多个子账号。

13. 家庭成员可拥有几台设备、一个设备可绑定几名家属？谁是最终管理员？  
    答：设计为多对多绑定关系，为了简单，暂时所有绑定设备的人，都具有管理员权限。

14. 屏幕尺寸、分辨率、是否触摸，以及表情素材由谁制作？是否已有角色 IP 和视觉规范？  
    答：已经制作全套表情包，后面开发阶段可以提供。屏幕是420*420像素的触摸屏。暂时没有角色IP设计。

15. 头部与底座更倾向 BLE 还是充电触点有线通信？是否需要头部可拆卸后继续工作？  
    答：硬件部分已经外包，不需要设计。

16. 声源跟踪是在唤醒后一次性转向，还是说话期间连续跟踪？附近多人说话时按什么规则选择？  
    答：说话期间连续跟踪。多人说话还没考虑，应该是根据对话内容，朝向主要对话人。

17. 方言目标仅为东北常用词和口音识别，还是需要自然生成细分到具体城市的方言？是否已有授权语料和母语评审人员？  
    答：暂时固定使用东北方言。没有做语料方面的工作。

18. 长期记忆中哪些信息可以自动记忆，哪些必须询问确认？老人本人和家属发生冲突时谁有修改权？  
    答：都自动记忆就可以。设置内容以老人语音为主，对于生效的设置，家属可以通过line修改设置。其它无关设置的，以老人语音为准。

19. 主动对话允许的时间、每天频次和关闭方式是什么？如何判断用户在场？  
    答：一定时间没人说话，雷达没有监测到人活动，或者晚上时段，就进入休眠。我们通过毫米波雷达判断是否有人在场。

20. 目标知识网站和内容文件有哪些？版权/抓取许可是否已确认？回答是否需要向用户展示或播报来源？  
    答：暂时没考虑。

21. 音乐/音频已有哪家版权服务或账号？是否接受第一阶段仅播放用户自有/明确授权内容？  
    答：打算接入喜马拉雅网站，还没开始研究如何接入。

22. 是否存在企业后台的客服、运营、审计角色？各自允许查看哪些用户信息？  
    答：暂时没考虑。

## 已追加并确认（2026-08-22）

27. 家属 App 登录方式？  
    答：邮箱和 LINE Login；一期不考虑手机号。2026-08-22 进一步确认采用建议方案：邮箱使用一次性验证码，不设置邮箱密码。

28. 老人能否通过语音执行敏感设置？  
    答：按建议实现。低风险偏好允许语音修改；删除账号、解绑最后一名家属、恢复出厂、长期数据导出/删除、安全联系人等敏感操作禁止仅凭语音执行，转家属 App/后台强认证和二次确认。声纹一期不作为敏感操作的唯一认证因素。

29. ESP32—Android 协议确认状态？  
    答：《ESP32-Android通信协议草案-v0.1.md》已准备发给外包方，等待确认；软件先使用协议模拟器和传输适配层推进。

30. 日本公共与本地生活信息服务？  
    答：新增专项需求。先设计统一来源调研、连接器、标准数据结构、来源透明和主动触发框架；具体来源由后续客户调研逐个确认。
