# 开源项目复用分析

> 版本：v0.1  
> 分析日期：2026-08-20  
> 分析基准：本地仓库当前工作树；未修改四个参考仓库。

## 1. 结论摘要

建议采用以下主次关系：

| 项目 | 定位 | 结论 |
|---|---|---|
| `xiaozhi-esp32-server` | 生产服务端代码基线 | 主干复用；保留 WebSocket 协议、Provider 和管理平台，进行安全与工程化加固 |
| `xiaozhi-android-client` | Android 14 机器人客户端代码基线 | UI/协议原型复用；音频管线、连接状态机和设备常驻能力需要重构 |
| `xiaozhi-esp32` | 协议与端侧行为参考实现 | 不进入 Android 构建；作为协议真值、状态机、MCP 和音频行为参考 |
| `py-xiaozhi` | Windows 演示、联调和自动化测试客户端 | 保留为开发工具；用于服务冒烟、协议回归、故障注入和音频回放 |

不建议从头重写协议或服务端，也不建议把 Android 项目按普通手机聊天 App 的形态直接投产。

## 3. 服务端复用设计

### 3.1 可直接保留

- `xiaozhi-server` 的 asyncio WebSocket 会话处理框架。
- `hello/listen/abort/stt/tts/emotion` 消息协议和 Opus 二进制音频承载。
- VAD、ASR、LLM、TTS、Memory、Intent Provider 抽象和动态配置机制。
- 流式 ASR/TTS、函数调用、MCP、短期记忆以及性能测试工具。
- `manager-api`（Spring Boot）、`manager-web`（Vue）、MySQL/Redis 基础管理能力。
- 设备绑定、Prompt/智能体配置的现有数据和页面作为原型。

### 3.2 应扩展而非重写

- 新增 `JapanSearchProvider`/MCP 工具边界，后续按白名单接入日本本地来源。
- 在现有 Provider 配置之上增加环境、设备组和策略版本，支持灰度和回滚。
- 在连接上下文中增加统一 `trace_id`、客户端版本、设备型号、地区和协议能力。
- 将老年慢语速参数做成用户/设备策略，不硬编码全局 VAD 阈值。
- 使用现有 `emotion` 消息扩展表情语义，但通过 `protocol_version/features` 协商，避免破坏 ESP32 兼容。

### 3.3 生产前必须补齐

1. 鉴权：禁止默认测试 Token；设备凭据唯一、可吊销，WebSocket 握手必须校验设备与绑定状态。
2. 密钥：API Key、数据库密码和 JWT 密钥进入 Secrets 管理，不进入仓库、镜像或日志。
3. 网络：公网只暴露 TLS 入口；Python 实时服务、manager-api、数据库和 Redis 使用私网隔离。
4. 可靠性：会话并发上限、超时、背压、优雅关闭、供应商熔断和限流。
5. 可观测：按 ASR/LLM/TTS 分段的延迟、错误、成本和 Trace；正文默认不写日志。
6. 测试：协议契约、Provider 契约、弱网/断线、并发和长稳测试。
7. 数据：明确音频/文本保存开关、期限、用户删除和审计链路。

上游 README 明确提示项目功能未完善且未通过网络安全测评，因此它适合作为研发基线，不构成可直接生产部署的安全证明。

### 3.4 首期建议部署组件

仅对话阶段仍建议部署完整的三组件最小集：

- `xiaozhi-server`：实时语音与 AI 编排。
- `manager-api`：设备、用户、智能体和模型配置。
- `manager-web`：内部运营配置。
- MySQL、Redis、反向代理/负载入口、日志指标系统。

`manager-mobile`、`digital-human`、RAGFlow、PowerMem、视觉服务暂不进入生产关键路径；`digital-human` 可保留为内部联调工具。

## 4. Android 客户端复用设计

### 4.1 当前可复用能力

- Flutter 页面、配置模型和基础会话 UI。
- WebSocket 连接及协议头：`device-id`、`client-id`、`protocol-version`、`Authorization`。
- `hello` 协商：Opus、16 kHz、单声道、60 ms 帧。
- PCM 采集、Opus 编解码、二进制音频发送与播放。
- `listen`、`abort`、`stt`、`tts`、`emotion` 消息处理。
- Android 麦克风、网络、音频和蓝牙权限声明作为起点。

### 4.2 已识别的关键技术债

| 问题 | 代码证据 | 影响 | 处理要求 |
|---|---|---|---|
| 录音块未做连续分帧 | `AudioUtil.encodeToOpus` 只编码首个 60 ms，短块补静音 | 丢音、节奏异常、ASR 准确率下降 | 使用 PCM ring buffer，逐个生成完整帧并保留余量 |
| 连接状态不真实 | `isConnected` 仅判断 channel/subscription 非空 | 握手前发送、假在线 | 显式 `DISCONNECTED/CONNECTING/HANDSHAKING/READY` 状态 |
| 定时发送 hello | 连接后固定延迟 200 ms | 慢网络竞态 | 等待 socket ready 后发送并设置握手超时 |
| 固定 3 秒重连 | 无指数退避、上限和网络感知 | 断网耗电、惊群 | 指数退避 + jitter + Android 网络回调 |
| Token/消息直接日志输出 | WebSocket 与 Service 多处 `print` | 凭据和对话泄露 | 结构化脱敏日志，Release 禁止正文/Token |
| 默认 `test-token` | 未启用 Token 时仍发送默认值 | 形成错误安全假设 | 生产构建强制安全注册和有效凭据 |
| 音频职责为全局静态类 | 共享 recorder/player/controller | 生命周期、重入和测试困难 | 拆分 Capture/Encoder/Playback 实例并注入 |
| 缺少客户端协议测试 | 测试主要覆盖 MiniMax，与小智音频链路无关 | 回归不可控 | 建 mock server、golden audio、状态机单测 |
| 缺少机器人常驻能力 | 无前台服务、开机恢复、kiosk 设计 | 黑屏/回收后不可用 | 增加 Android 原生 Service/Device Owner 集成层 |
| 缺少 AEC 与端侧 VAD | 当前持续上传，依赖服务端 VAD | 自激、带宽、无法自然打断 | MTK Audio HAL/AEC 优先，端侧 VAD 作为阶段二 |

### 4.3 建议客户端分层

```text
Flutter UI / 表情层
        │
ConversationController（唯一状态机）
        ├── XiaozhiProtocolClient
        ├── AudioCapture → PCM FrameBuffer → OpusEncoder
        ├── OpusDecoder → AudioPlayback
        ├── AudioPolicy（焦点、AEC、路由、音量）
        ├── DeviceIdentity / SecureStore
        └── Telemetry
                │ Platform Channel
Android Robot Service（Foreground Service、开机启动、kiosk/看门狗）
```

Flutter 继续承载界面和大部分业务；与 MTK 音频 HAL、系统级 AEC、开机启动、前台服务和设备管理相关的能力放到 Kotlin 插件层。这样既保留现有项目价值，也避免在 Dart 层模拟系统能力。

### 4.4 Android 14 专项

- 使用 `targetSdk 34` 作为 Android 14 基线；当前本地修改已设置该值，但 `compileSdk 36` 与插件强制版本逻辑需要清理并锁定可复现构建。
- 生产包必须使用正式签名；当前 Release 使用 debug signing，仅可开发测试。
- 机器人若需持续采音，必须设计合规的麦克风前台服务及可见状态；如设备为专用终端，优先采用 Device Owner/kiosk 管理而非普通消费 App 后台保活技巧。
- 与 MTK 厂商确认 Audio HAL 是否提供 AEC/NS/AGC、阵列输入通道、采样率、音频路由和同时录放能力。
- 删除机器相关的绝对 Gradle/JDK 路径，使用项目工具链定义和 CI 缓存，确保任意开发机可构建。

## 5. ESP32 项目的参考边界

只借鉴下列逻辑：

- WebSocket/MQTT 消息语义和能力协商。
- `IDLE/CONNECTING/LISTENING/SPEAKING` 状态流转。
- Opus 帧和音频收发节奏。
- MCP/IoT 描述与消息格式。
- 断线、重连、打断和 OTA 的行为预期。

不直接移植 ESP-IDF 驱动、板级代码和 FreeRTOS 任务模型到 Android。协议以独立 JSON Schema/契约测试固化，不能依赖“阅读某个 ESP32 版本源码”维持兼容。

## 6. Python 客户端的测试定位

`py-xiaozhi` 已包含 WebSocket/MQTT、Opus、状态管理、唤醒和 AEC 文档，可改造成：

- CI 中的无硬件协议客户端。
- 固定音频输入的 ASR/延迟回归工具。
- 服务端 `hello/listen/abort` 契约测试。
- 网络断开、消息乱序、供应商超时的故障注入工具。
- Windows 上的产品演示客户端。

不将其作为 Android 生产代码来源，也不以 Windows 系统 AEC 结果证明 MTK Android 声学链路合格。

## 7. 日本部署约束

- 业务入口、数据库、日志和对象存储优先选择日本区域。
- 对 ASR/LLM/TTS 的每个候选供应商记录实际处理国家、再委托方、保留期和训练使用政策。
- 若语音或转写发送给日本境外第三方，需在上线前由日本隐私专业人员按 APPI 审查。日本个人信息保护委员会关于向境外第三方提供个人数据的指南要求在相应情形下提供目的国、当地制度及接收方保护措施等信息并取得同意；具体适用方式不能由技术文档替代法律意见。[PPC 境外提供指南](https://www.ppc.go.jp/personalinfo/legal/guidelines_offshore/)
- 用户界面至少预留日文隐私告知、同意记录、撤回、导出和删除入口；第一批用户语言仍需确认。
- 日本本地搜索通过服务端受控工具实现，来源白名单、缓存时效、出处和失败降级待用户提供具体信息后定稿。

## 8. 开发前基线动作

1. 为四个 fork 建立内部基线 tag 和 `UPSTREAM.md`。
2. 审查服务端落后的上游提交，选择升级窗口；冻结后不随意追主分支。
3. 将本地开发配置中的数据库凭据视为已暴露并轮换，改用环境变量/Secret；检查 Git 历史和日志。
4. 清理 Android 构建的绝对路径、debug signing、Token 日志和默认测试凭据。
5. 建立 `protocol-contract` 目录，集中保存 schema、示例和兼容测试。
6. 生成依赖 SBOM，执行许可证、Secret 和已知漏洞扫描。
